Part 1 · How the project was produced
From one-line request to a delivered report

The production process, made visible

The user asked JiuwenSwarm to “analyze a US-listed company, forecast its price, and produce an investment research report — while learning how to develop multi-agent systems.” Below is how the platform turned that into a running pipeline.

Course positioning: this demo also serves as the Risk Management teaching case for the IEDA4000H theme — the Risk & Sentiment Analyst outputs a risk checklist, a risk rating and position-sizing advice, while the forecast attaches up/down probabilities with a confidence level, showing that risk output must carry indicators, assumptions, limitations and evidence.

1.1 Team composition

Leader + 7 agents, each with a clear boundary

Every agent carries a role description following the golden formula: who you are + your expertise + what you own + what you are NOT responsible for. Clear boundaries keep the DAG conflict-free.

team-leader · Teaching controller

Builds the team, decomposes the task DAG, coordinates members, accepts deliverables — and narrates every step as a lesson.

Produces: verified deliverables + live teaching narration

data-researcher · First stage

Data engineer. Prepares and validates local sample datasets (financials + weekly prices). NOT responsible for analysis or forecasts.

Integrates every upstream deliverable into one final package: research report, teaching handbook, and student lab worksheet.

qa-tester · Quality gate

Independent verification agent. Reads every analysis and forecast, cross-checks every number against the source CSVs, and rules PASS/FAIL with evidence. NOT responsible for writing analyses.

Produces: PASS/FAIL verdict + evidence checklist per deliverable

Key insight: four design rules — one-way flow (no cycles), parallel decoupling (three analysts share one prerequisite), single convergence point (all analyses feed exactly one forecast task), and an independent quality gate (QA verifies every analysis against the source data before synthesis; FAIL sends the work back for rework).

1.3 Collaboration timeline

From build_team to delivery, step by step

What actually happened during the run — including one instructive incident that became a core teaching point.

Phase 1 · Setup
build_team

Create the team

Team “US Equity Research Multi-Agent Teaching Demo” (id task-3e864b925b) is created with a shared workspace .team/.

Phase 1 · Setup
spawn_teammate ×7

Spawn the seven role agents

Data researcher, three analysts, independent QA, forecaster, report synthesizer — each with a boundary-rich description.

Phase 1 · Setup
create_task ×7

Wire the task DAG

Seven tasks with explicit blocked_by dependencies — the DAG self-schedules as upstream completes.

Phase 2 · Kickoff
send_message(to="*")

Kickoff broadcast

Leader broadcasts: “Data task starts first; other tasks wait for data to be ready.” Members self-claim their tasks.

Phase 3 · Data
claim_task · .team/ handoff

Data researcher produces the sample datasets

financials.csv (FY2022–FY2025, 14 fields) and stock_history.csv (53 weekly OHLCV bars) are written to .team/demo-data/.

Phase 3 · Real incident
Verification gate

False completion caught by actual inspection

The data researcher first reported “task-data complete.” The Leader did not trust the report — he actually opened the shared folder and found no CSV files. Downstream was paused, the data was regenerated, re-checked, and only then accepted.

Teaching point: acceptance must be based on reading the deliverable, not on the reporter’s word. “Verify, don’t just trust the report.” This is why verify_task exists as a quality gate.
Phase 4 · Parallel analysis
3 tracks in parallel

Three analysts read the CSVs, write their reports

fundamental.md (66/100), technical.md (Bullish), risk.md (Medium–high) — all converge into the shared .team/analysis/.

Phase 5 · Independent QA
verify_task · reviewer gate

QA tester cross-checks every analysis

The independent QA agent (qa-tester) verifies each analysis against the source CSVs and acceptance criteria, ruling PASS (with evidence) or FAIL (back for rework) before any number reaches the forecaster.

Two-level gate: the QA reviewer and the Leader both rule PASS/FAIL — independent verification first, Leader acceptance last.
Phase 6 · Synthesis
task-forecast

Forecaster builds the combined forecast

PEG valuation test + PE×EPS three-scenario weighting → target 215–365, mid ≈310, up/down 45/55, confidence 60%.

Phase 7 · Integration
task-report

Report synthesizer assembles the final package

Investment research report + multi-agent development handbook + student lab worksheet, all with a teaching disclaimer.

Phase 8 · Acceptance
verify_task · deliver

Leader verifies and delivers to the user

Every file is inspected against the task requirements; pass/fail rulings close the loop, then the package is handed over.
